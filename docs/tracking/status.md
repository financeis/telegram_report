## 남은 것 (먼저 할 것부터)

1. **그림 리포트·발행처 작업의 운영 적용 마저 하기(멈춘 곳부터).** 2026-10-10에 저장 없는 시험을 통과하고, 첫 묶음 `tag requeue --unreadable --publisher-not-in-dictionary --apply`로 대기 줄에 되돌린 뒤(백업 `backups/requeue/requeue-20261010-024105.csv`) 백필을 돌리다가 사용자 요청으로 멈췄다. **대기 줄에 남은 행은 이 작업의 분류기로만 처리한다 — 이 작업이 들어가기 전 코드로 백필을 돌리면 옛 방식으로 분류된다.** 남은 순서: (1) 웹앱·수집을 끄고 `run-batches.ps1`로 남은 대기를 처리한다(비율은 다시 분류된 행끼리 본다). (2) 둘째 묶음 `tag requeue --publisher-filename-mismatch --publisher-type-mismatch`를 미리 보기 → `--apply` → 백필. (3) 두 백업과 지금 값을 비교해 발행처가 바뀐 리포트가 들어간 저장된 비교를 한 번 비운다(`docs/operations.md`). (4) 쉬운 말로 결과를 보고한다: 단계별 건수, 다시 분류된 행의 발행처가 모두 정식 이름이거나 비었는지, 그림 행의 결과와 의심 표시 수, 비운 비교 수, 사람이 승인한 행 가운데 옛 발행처 이름을 가진 행 수, 그림 리포트가 이미 있는 글자 리포트의 중복인지. 백필 중 비정상 종료 횟수를 세어 `docs/operations.md`의 "잠금 뒤 재측정" 줄에 더한다.
2. **종목표 교체(바로 다음 작업).** 사용자가 올린 새 종목표 파일은 칸 구성과 산업 분류 체계가 달라 설계부터 한다(`findings.md`). 바꾼 뒤 `stocks set-version`과 `tag requeue --krx-unmatched`로 쌓인 미매칭 행을 다시 분류한다.
3. **발행처 직접 고르기 화면.** 의심 표시(`publisher_suspect:*`)가 붙은 행과, 사람이 승인해 옛 발행처 이름이 남은 행을 사람이 고치는 화면(`findings.md`).
4. **정기 수집·분류.** 2026-10-09에 수집(9월 초 메시지부터 그날까지)과 분류 백필을 따라잡았다. 수집은 아직 예약 작업이 아니라 사람이 `python -m research_desk collect`로 돌리고, 쌓인 분류 대기는 `powershell -File scripts\run-batches.ps1 -Iterations N -BatchSize 10`으로 처리한다(첫 몇 배치의 JSON 보고와 `tag inspect` 비율을 확인한다). 빠진 번호가 의심되면 `collect --dry-run --backfill-days N`으로 본다.
5. **웹앱 실제 실행.** `powershell -File scripts\start-workspace.ps1`(또는 `python -m research_desk web`)로 다시 켜서 화면 전체를 한 번 써 본다.
6. **기업간 유사도 실제 데이터 단계(사용자와 함께, 이 순서로).**
   1. `.env`에 `KIS_APP_KEY`·`KIS_APP_SECRET`을 넣는다(값은 사용자가 넣는다).
   2. 마이그레이션 008을 Supabase SQL 편집기에서 적용한다(pgvector 확장 위치를 먼저 확인).
   3. `python -m research_desk prices update --codes 005930,080220`으로 KIS 접속과 필드 해석을 확인하고(아무것도 저장하지 않음), 전체 실행을 한 번 한 뒤 작업 스케줄러에 등록한다.
   4. 텔레그램 수집·분류를 최신으로 유지한다(4번). 리포트 수가 그만큼 정확해진다.
   5. DART 수집 프로그램(별도 저장소)을 고쳐 `FS.A001_v2`를 `parser_version` 0.2.0 이상으로 채운다.
   6. 시험 실행(`peers build --pilot`)으로 품질을 점검하고, 프로필 모델을 고르고, 전체 비용·시간을 보고해 승인받는다.
   7. 전체 `peers build` → 제주반도체 기업 화면의 유사 기업 탭, "레거시 DRAM" 테마 검색, 상태 줄을 실제 데이터로 확인한다.
7. **화면 코드 분할(다음 코드 작업).** `frontend/src/main.jsx` 한 파일에 메뉴·화면 전환과 기업 리서치·분석·비교 화면이 들어 있다(커버리지·검토는 `Coverage.jsx`·`ReviewQueue.jsx`). 유사 기업 탭·테마 검색(`frontend/src/peers/`)과 상태 줄(`frontend/src/freshness/`)은 이미 기능별 폴더에 있고 `main.jsx`는 연결만 한다. 나머지를 메뉴·화면 전환 틀 / 공용 부품 / 기능별 폴더로 나누고, 한 기능의 서버 폴더와 화면 폴더 이름을 맞춘다. 화면 주소의 보기 이름(`?view=market` 등)과 서버 주소(`/api/market`)는 호환을 위해 둔다. 화면 쪽에 따로 복사된 분석 대상 외 사유 목록을 공용 기준(`domain/vocabulary.yaml`)과 맞춘다. 분할 전후 화면이 같은지 캡처로 비교한다. 화면 폴더의 작업 안내도 이때 만든다.
8. **수급 데이터 분석.** 외부 데이터 받기, 자기 표, 계산, 화면으로 붙는 새 기능 폴더. 데이터 출처는 붙일 때 정한다.
9. **퀀트 연결.** 주가·공시 데이터를 붙여 리포트의 전망 변화와 실제 주가·실적을 비교·검증한다. 당시 쓸 수 있었던 정보만 쓰는 시점 규칙이 핵심이다. 주가 데이터의 주인은 `features/prices`이고 지금은 종목당 최신 스냅샷만 있으므로, 일별 이력이 필요하면 이 기능에 더한다.
10. **종목표 자동 갱신.** API로 종목표를 받아 CSV와 버전 정보를 함께 쓴다(`domain` 자리). 날짜별 보관(상장·폐지 이력)은 퀀트 연결과 함께 정한다.
11. **예약 작업의 실패 알림.** 첫 답은 모든 화면 맨 위의 상태 줄(주가·리포트 기준일, 밀리면 빨간색)이다. 남은 것: 앱을 열지 않아도 알리는 방법(텔레그램 알림 등), 수집을 예약 작업으로 만들 때 그 기준일을 상태 줄에 더하기.
12. **유사 기업 후속(정하지 않음).** 공급망(고객사) 화면, 리포트에서 시작하는 수혜주 묶음, 백테스트, 반기보고서로 갱신, 유사 결과에 대한 사용자 피드백, 주가 차트.
13. **다른 기기 접속(시점 미정).** 이 PC가 계속 서버가 될지 클라우드로 옮길지 미정이다. 접근 제어는 웹 조립부 한 곳에 붙인다.
14. **그 밖의 기능.** 계속 붙일 예정이고, 무엇을 언제 붙일지는 미정이다.
