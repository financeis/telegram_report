# 0001 — 파이썬 코드를 패키지 하나에 두고, 칸 경계는 자동 검사로 지킨다

## 배경
웹앱·분석·검토 코드가 분류기 폴더(`langgraph_tagger/`) 안에 있었고, 수집기는 루트에 흩어져 있었다. 설정 읽는 코드가 4벌, 종목표 읽는 코드가 2벌이었고, "분석 대상 리포트"의 정의가 여러 곳에 따로 적혀 있었다. 앞으로 수급 분석·기업간 유사도·퀀트 연결 같은 기능이 계속 붙는데, 개발은 주변 코드를 따라 하는 AI 코딩 도구(Claude Code·Codex)로 한다. 자리와 규칙이 분명하지 않으면 새 기능이 아무 데나 붙고 서로 내부를 가져다 쓰게 된다.

## 결정
- 파이썬 코드 전체를 `research_desk` 패키지 하나에 둔다. 칸은 `core`(공용 설비), `domain`(공용 기준), `collector`, `tagger`, `features/<기능>`, `web`(조립·등록만), 명령 입구(`cli.py`·`__main__.py`).
- 칸 사이 경계(누가 누구를 import할 수 있는지, 외부 도구를 어느 칸에서만 쓰는지, 표 주인)는 `research_desk/tests/test_architecture.py`가 모든 테스트 실행에서 검사한다.
- 새 기능 = 새 폴더 하나 + 등록 한 줄(웹 기능 목록, 필요하면 명령 목록).
- 기능끼리는 상대의 `__init__.py`가 명시적으로 묶은 이름으로만 주고받는다.

## 버린 대안
- **저장소·서비스 분리**(수집기·분류기·웹앱을 따로): 혼자 쓰는 로컬 앱에서 배포·버전 맞추기·공용 코드 복제만 늘어난다. 세 단계가 같은 표와 같은 분류 체계를 공유해서 분리 이득이 없다.
- **폴더만 나누고 규칙은 문서로**: 사람이든 AI든 문서를 안 읽으면 그만이다. 실제로 테스트가 일부만 돌던 일이 있었다. 검사가 실패해야 지켜진다.

## 결과
- 경계를 어기는 import·표 접근은 테스트와 커밋에서 실패한다. 새 칸이나 새 표를 만들면 검사 규칙(칸 목록, 표 주인 목록)도 같이 고쳐야 한다.
- 기능이 다른 기능의 내부 모듈을 직접 쓸 수 없다. 필요한 이름은 그 기능의 `__init__.py`에 공개해야 한다.
- `core`는 업무 개념을 모르므로 "리포트"·"종목" 같은 규칙을 `core`에 둘 수 없다. 여러 칸이 같이 쓰는 업무 규칙은 `domain`에 둔다.
- 옮긴 파일의 git 이력은 새 경로에서 처음부터 시작한다. 옛 이력은 옛 경로(`langgraph_tagger/…`, 루트 `collector.py` 등)로 본다.
