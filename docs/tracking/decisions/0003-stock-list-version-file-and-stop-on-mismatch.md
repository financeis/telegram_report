# 0003 — 종목표 버전은 버전 정보 파일이 정하고, 내용이 다르면 분류를 멈춘다

## 배경
`reports.taxonomy_version`에는 분류에 쓴 종목표(KRX CSV)의 버전이 들어간다. 예전 분류기는 이 값을 CSV 파일의 수정 시각으로 만들었다. 그 결과 같은 내용의 종목표(git 커밋은 하나뿐)가 작업 폴더마다 다른 수정 시각을 가져 `KRX@2026-05-08`·`KRX@2026-05-09`·`KRX@2026-05-12` 세 표시로 갈렸다. 같은 내용에 다른 표시가 붙으면 나중에 "어느 종목표로 분류했나"를 믿을 수 없다(퀀트 연결 때 중요).

## 결정
- 종목표와 같은 폴더의 버전 정보 파일(`KRX_stocks_data.version.json`)이 `{"version": "KRX@<자료 기준일>", "content_hash": "<내용 지문>"}`을 든다. 분류 결과에는 이 `version`을 쓴다.
- 지문은 파일 바이트가 아니라 CSV로 해석한 칸 값으로 계산한다(줄바꿈 방식·따옴표 표기 무시, 칸 값·행 순서는 반영).
- 분류 명령(`tag run`, `tag escalate`)은 시작할 때 지문을 확인하고, 버전 정보가 없거나 다르면 행을 가져가기 전에 종료 코드 4로 멈춘다. `stocks set-version --as-of <자료 기준일>`이 버전 정보를 갱신한다.
- 웹앱은 버전을 저장하지 않으므로 경고만 남긴다.
- 기존 DB의 세 표시는 `KRX@2026-05-08`로 통일했다(마이그레이션 007, 바뀐 행 백업 후 한 번 실행).

## 버린 대안
- **경고만 하고 계속 분류**: 내용이 바뀐 종목표에 옛 표시가 붙는다.
- **내용이 바뀌면 자동으로 새 버전 이름을 만듦**: 기준일을 알 수 없어 날짜가 의미를 잃고, 표시 갈래가 다시 생긴다.
- **파일 바이트로 지문 계산**: 이 저장소는 `core.autocrlf=true`라 작업 폴더의 CSV는 CRLF, 저장소에는 LF다. 바이트 지문은 작업 폴더마다 달라져 모든 곳에서 분류가 멈춘다.

## 결과
- 종목표를 바꾸는 사람은 반드시 `stocks set-version`을 실행하고 CSV와 버전 정보 파일을 한 커밋에 올려야 한다. 함께 들어 있는 CSV와 버전 정보 파일의 지문이 같은지 테스트가 확인한다.
- 버전 이름은 "자료 기준일"이라서 같은 날짜로 다시 쓰는 것은 허용한다. 서로 다른 내용에 같은 날짜를 쓰지 않도록 기준일을 정확히 넣는 것은 사람의 몫이다.
- 리포트 분류 체계 파일(`domain/vocabulary.yaml`)에는 버전이 없다. 그 값이 바뀌면 DB 제약 변경(마이그레이션)이 함께 필요하다.
