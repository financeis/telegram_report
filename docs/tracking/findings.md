# 아직 못 푼 문제

## `tag escalate`가 상태를 확인하지 않고 덮어쓴다
- **증상.** `tag escalate --since <시각>`이 대상 `review_needed` 행을 고른 뒤 `id`로 다시 분류해 쓴다. 고른 뒤 쓰기 전에 사람이 검토 화면에서 같은 행을 승인·제외·재분류하면, 그 검토 결과를 재처리 결과가 덮어쓴다.
- **영향.** 검토한 행의 결과가 사라진다(되돌리기 스냅샷도 "후속 작업이 처리한 보고서"로 거절된다). 검토 화면과 `escalate`를 동시에 쓸 때만 생긴다.
- **지금 못 고치는 이유.** 재처리 명령의 동작을 바꾸는 일이라 사용자가 정해야 한다. 쓰기에 상태 조건을 넣으면 "덮어쓰지 못한 행"을 보고하는 방식과 테스트도 새로 정해야 한다.
- **방법.** 쓰기 SQL에 `tagging_status = 'review_needed'`(또는 가져가기 표시) 조건을 넣고, 조건에 걸린 행은 보고에 따로 센다.

## `tag run --row-ids`가 상태와 상관없이 다시 분류한다
- **증상.** 지정한 행을 `pending`으로 가져가는 표시 없이 바로 분류해 쓴다. 같은 행을 다른 작업자가 `processing`으로 가져간 상태면 둘이 겹쳐 쓴다(마지막 쓰기가 이긴다).
- **영향.** 백필 중에 `--row-ids`를 돌리면 같은 행이 두 번 분류되고 토큰이 두 배로 든다. 데이터 모양은 어느 쪽이든 정상 분류 결과다.
- **지금 못 고치는 이유.** 명령의 동작을 바꾸는 일이라 사용자가 정해야 한다. `--row-ids`는 이미 `auto`·`verified` 행을 다시 분류하는 유일한 길이라, 막는 대신 가져가기 표시를 붙이는 방식으로 바꿔야 한다.
- **방법.** `--row-ids`도 `FOR UPDATE SKIP LOCKED`로 가져가기 표시를 붙이고, 이미 `processing`인 행은 건너뛰고 보고한다.

## 종목표에서 사라진 종목은 관심 기업에서 뺄 수 없다
- **증상.** `PUT /api/favorites/{code}`는 켜기·끄기 모두 먼저 종목표에 그 코드가 있는지 본다. 종목표를 새로 바꾸면서 빠진 종목(상장 폐지 등)은 끄기 요청도 404 `종목을 찾을 수 없습니다.`다.
- **영향.** 화면의 관심 기업 목록에 그 코드가 계속 남는다. 파일(`~/.review_viewer/favorites.json`)을 손으로 고쳐야 한다.
- **지금 못 고치는 이유.** 동작을 바꾸는 일이라 사용자가 정해야 한다(지금 동작은 테스트로 고정돼 있다).
- **방법.** 끄기(`enabled: false`)는 존재 확인 없이 허용한다.

## 깨진 관심 기업 파일이 두 번째로 깨지면 기업 목록이 503이 된다
- **증상.** 관심 기업 파일이 깨지면 읽을 때 `favorites.json.bak`으로 이름을 바꾸고 빈 목록으로 본다. UTF-8이 아닌 파일도 같은 길로 간다. 이미 `.bak`이 있으면 윈도우에서 이름 바꾸기가 실패해 `GET /api/workspace`가 일반 503으로 끝난다.
- **영향.** 기업 검색·관심 기업 화면이 막힌다. `.bak` 파일을 지우면 회복한다.
- **지금 못 고치는 이유.** 관심 기업 파일의 복구 방식(기존 `.bak`을 덮을지, 여러 개를 남길지)을 바꾸는 일이라 사용자가 정해야 한다.
- **방법.** 이름 바꾸기를 `os.replace`로 해서 기존 `.bak`을 덮어쓰게 한다(또는 `.bak` 이름에 시각을 붙인다).

## 같은 PDF가 여러 메시지로 들어오면 두 번 센다
- **증상.** 행의 정체는 `(채널, 메시지 번호)`다. 같은 PDF가 다른 메시지로 다시 올라오면 별도 행이 되어, 리포트 목록과 커버리지 집계에 두 번 나온다. `file_hash_sha256`은 저장돼 있지만 묶지 않는다.
- **영향.** 커버리지 숫자(종목별 다뤄진 횟수, 발행량)가 부풀 수 있다. 분석·분류 비용도 두 번 든다.
- **지금 못 고치는 이유.** 같은 PDF를 하나로 볼지, 어느 행을 남길지(먼저 받은 것? 분류가 끝난 것?)는 사용자가 정할 업무 규칙이다.
- **방법.** 규칙이 정해지면 수집 때 같은 지문의 기존 행을 찾아 표시하거나, 집계 쪽에서 지문 단위로 센다.

## 재무 추출 프롬프트가 목표주가 방향 값으로 `유지`를 안내한다
- **증상.** 추출 프롬프트의 정규화 규칙 3은 `target_price_dir`을 `상향 / 하향 / 유지 / 신규 / N/A`로 안내한다. 응답 스키마와 DB 제약이 허용하는 값은 `상향·불변·하향·신규·N/A`다(`유지`는 투자의견 방향의 값이다).
- **영향.** 형식을 강제하는 경로(OpenAI·Codex의 출력 스키마)에서는 모델이 `유지`를 낼 수 없어 문제가 드러나지 않는다. Claude 모델로 분석을 돌리면(형식 강제 없이 JSON을 검증하는 경로) 모델이 `유지`를 내는 순간 응답 검증이 실패해 그 분석이 형식 오류로 끝난다. 검증이 목표주가 방향을 산수로 다시 정하는 단계보다 먼저 일어나므로 목표주가가 몇 개 있든 같다. 목표주가가 그대로인 리포트(새·옛 값이 같음)에서 가장 일어나기 쉽다.
- **지금 못 고치는 이유.** 프롬프트 문구를 바꾸면 추출 결과 전체가 달라질 수 있어, 같은 리포트 묶음으로 다시 비교 측정한 뒤 사용자가 정해야 한다.
- **방법.** 규칙 3의 `유지`를 `불변`으로 고치고, 측정용 리포트 묶음으로 추출 결과를 비교한다. 스키마에 `유지`를 더하지는 않는다(DB 제약과 화면이 `불변`을 쓴다).

## 커버리지 계산이 "분석 대상" 규칙의 절반을 다시 적고 있다
- **증상.** 커버리지 계산(`features/coverage/logic.py`)은 리포트 창구에서 받은 행 가운데 `out_of_scope_reason`이 비어 있는 것을 분석 대상으로 친다. 상태 조건(`auto`·`verified`)은 보지 않는다. 리포트 창구가 늘 그 두 상태의 행만 넘기기 때문에 지금은 결과가 맞다. 공용 기준의 `is_in_scope`는 운영 코드 어디서도 쓰이지 않는다.
- **영향.** 리포트 창구가 다른 상태의 행도 넘기게 바뀌면(예: 검토 대기 행까지 세는 화면을 더할 때) 커버리지가 그 행들을 분석 대상으로 잘못 센다. "분석 대상 정의는 공용 기준 한 곳에만"이라는 규칙과도 어긋난다.
- **지금 못 고치는 이유.** 계산 함수들은 상태 열이 없는 표도 받도록 짜여 있고, 그 계산을 검증하는 테스트들도 일부 열만 가진 표로 만든다. 공용 기준 규칙으로 바꾸려면 계산 함수가 받는 표의 모양(필수 열)과 테스트 자료를 함께 바꿔야 한다. 커버리지 계산의 약속을 바꾸는 일이라 그 기능을 다음에 고칠 때 함께 한다.
- **방법.** 공용 기준에 표 단위로 쓸 수 있는 판정 도우미(빈 값 처리 포함)를 두고, 커버리지 계산과 리포트 조회가 그것을 쓰게 한다. 계산 함수의 필수 열에 `tagging_status`를 더하고 테스트 자료를 맞춘다.

## 기능마다 준비 코드가 복사돼 있다
- **증상.** 종목표 준비(읽기 + 버전 경고 문구 + `NotReady`)가 기업 목록·리포트·커버리지·유사 기업에, DB 준비(설정 확인 + 고정 문구 + 연결)가 리포트·검토·분석·주가·유사 기업에, LLM 응답 확인 도우미가 분석·비교에 따로 들어 있다. 명령 쪽에도 DB 설정 확인과 종목표 읽기가 `prices update`·`peers build`에 따로 있다.
- **영향.** 동작은 같고 테스트도 각자 있다. 다만 새 기능을 붙이는 사람은 이 중 하나를 또 복사하게 되고, 문구나 규칙을 바꿀 때 몇 곳을 같이 고쳐야 하는지 놓치기 쉽다.
- **지금 못 고치는 이유.** 한곳으로 모으려면 공용 도우미의 자리를 정해야 한다. 종목표 준비를 공용 기준(`domain`)에 두면 `domain`이 설정 읽기(`core.settings`)를 쓰게 되고, DB 준비 실패 문구를 공용 설비(`core`)에 두면 `core`가 화면 문구를 갖게 된다. 칸 경계에 관한 설계 결정이라 사용자가 정한다.
- **방법.** 도우미의 자리를 사용자와 정하고, 위 기능들의 준비 코드를 그 도우미로 바꾼다(기능 쪽에는 자기 기능 이름만 남긴다).

## 화면 쪽에 분석 대상 외 사유 목록이 따로 복사돼 있다
- **증상.** `frontend/`가 사유 5개(`foreign`, `fund`, `digital`, `private`, `ir_self`)를 자기 코드에 따로 적고 있다. 공용 기준(`research_desk/domain/vocabulary.yaml`)에 사유를 더하거나 바꾸면 화면은 모른다.
- **영향.** 새 사유가 검토 화면의 선택지에 나오지 않는다(서버는 받지만 화면이 못 보냄).
- **지금 못 고치는 이유.** 화면 코드를 고쳐야 하는 일이고, 화면 코드는 화면 분할 작업에서 한꺼번에 나눈다.
- **방법.** 서버가 값 목록을 주는 주소를 두고 화면이 그것을 쓰게 하거나, 화면 분할 때 한 곳으로 모은다.

## 쪽 나누기 읽기가 같은 쿼리에 `range()`를 거듭 부른다
- **증상.** 1000행이 넘는 읽기에서 두 번째 쪽부터 요청 주소에 `offset`·`limit`이 두 번 이상 실린다. 지금 쓰는 postgrest-py(2.x)의 `range()`가 값을 바꾸지 않고 덧붙이는데, 리포트 기능의 `_paged_fetch`(기간·종목·여러 종목 읽기)와 유사 기업 기능의 `PeersStore._paged`(프로필·부문·임베딩·빌드 목록)는 같은 쿼리 객체에 쪽마다 `range()`를 다시 부른다. PostgREST가 겹친 값 중 마지막 것을 쓴다는 가정에 기대는 셈이다. 기존 기간 읽기가 실제 DB에서 쓰여 왔다는 점은 그 가정의 정황이지만, 쪽이 넘어가는 경우를 실제 서버에서 직접 확인한 기록은 없다. 같은 저장소 안에서 주가 기능은 쪽마다 새 쿼리를 만들고 그 가짜 DB는 두 번째 `range()`를 거절하는 반면, 리포트·유사 기업의 가짜 DB는 마지막 값을 쓴다.
- **영향.** 가정이 틀리면 1000행이 넘는 모든 쪽 나누기 읽기가 첫 쪽을 끝없이 다시 읽는다 — 커버리지 화면, 리포트 수(유사 기업 탭), 유사도 계산의 프로필·임베딩 목록이 멈추거나 메모리를 채운다.
- **지금 못 고치는 이유.** 실제 DB로 확인해야 하는데 이번 작업은 실제 DB에 닿지 않았다. 고치려면 두 기능의 저장 코드와 그 가짜 DB를 함께 바꿔야 한다(테스트가 지금 동작을 고정한다).
- **방법.** 실제 DB에서 1000행이 넘는 읽기 하나로 쪽마다 다른 행이 오는지 확인한다. 확인과 상관없이 안전하게 하려면, 두 저장 코드를 쪽마다 새 쿼리를 만드는 방식(주가 저장 코드의 `read_all_returns`)으로 바꾸고 두 가짜 DB가 두 번째 `range()`를 거절하게 한다.

## 날짜 글자의 형식이 섞이면 유효 날짜가 비어 행이 빠진다
- **증상.** 리포트 창구(`features/reports/store.py`의 `_effective_dates`)와 커버리지 계산(`_ensure_effective_date`)은 `pd.to_datetime(…, errors='coerce')`로 날짜 글자를 푼다. pandas 2는 첫 값으로 형식을 정해 나머지에 그대로 적용하므로, 한 번에 읽은 행들의 형식이 다르면(앞 행은 `…T09:12:00+00:00`, 다른 행은 소수 초가 붙은 `…T09:12:00.123456+00:00`) 다른 형식의 값이 오류 없이 빈 날짜(NaT)가 된다. 설치된 pandas 2.3에서 재현된다.
- **영향.** 유효 날짜는 `published_at`이 없을 때만 `sent_at`을 쓰므로, 빈 날짜가 되어 기간 거르기에서 빠지는 것은 `published_at`이 비어 있는 분석 대상 외 행이다 — 리포트 종류별 발행량(분석 대상 외 포함)이 덜 센다. 분석 대상 행은 늘 `published_at`(날짜만)이 있어 리포트 수 세기에는 거의 닿지 않는다.
- **지금 못 고치는 이유.** 이전 앱부터 내려온 동작이고 바꾸면 기존 커버리지 숫자가 달라질 수 있다. 실제 DB가 `sent_at`을 어떤 형식들로 돌려주는지(텔레그램 시각은 초 단위라 소수 초가 없을 수 있다) 먼저 확인해야 한다.
- **방법.** 두 곳에 `format='ISO8601'`을 주고, 형식이 섞인 행으로 테스트를 더한다.

## KIS 응답 필드의 뜻을 실제 서버로 확인하지 않았다
- **증상.** 시가총액은 현재가 응답의 `hts_avls`를 억원 단위로 보고 1억을 곱한다. 거래정지는 `temp_stop_yn = Y` 또는 종목 상태 코드 `iscd_stat_cls_code = 58`, 관리종목은 `mang_issu_cls_code = Y` 또는 상태 코드 `51`로 판단한다. 일봉은 수정주가(`FID_ORG_ADJ_PRC = 0`)로 받는다. 모두 사용자의 다른 프로젝트 구현과 KIS 문서를 보고 정한 값이고, 테스트는 가짜 KIS 응답만 쓴다.
- **영향.** 단위가 틀리면 화면의 시가총액이 자릿수째 틀린다. 상태 코드 해석이 틀리면 거래정지 종목이 거래 중으로 보여 후보로 뜨거나, 정상 종목이 `not_traded`로 후보에서 빠진다.
- **지금 못 고치는 이유.** KIS 키가 아직 `.env`에 없고, 이번 작업은 실제 KIS를 부르지 않았다.
- **방법.** 키를 넣은 뒤 `prices update --codes 005930,080220`(아무것도 저장하지 않음)의 `market_cap`이 HTS의 시가총액과 같은 자릿수인지, `traded`·`flags`가 맞는지 본다. 알려진 거래정지·관리종목 하나도 함께 넣어 본다.

## KIS 클라이언트가 전송 오류가 아닌 httpx 오류를 그대로 올린다
- **증상.** `core.kis.KisClient._call`은 httpx의 전송 오류(`TransportError`: 시간 초과·연결 끊김 등)만 잡아 다시 시도하거나 `KisError`로 바꾼다. 응답 본문을 풀다 난 오류(`httpx.DecodingError`, 깨진 압축 응답 등) 같은 그 밖의 httpx 오류는 다시 시도도, `KisError`로 바꾸기도 없이 그대로 올라간다. 모듈 설명은 "그 밖의 실패는 `KisError`"라고 적고 있다.
- **영향.** 작다. `prices update`는 종목마다 모든 예외를 그 종목의 실패로 세고, 토큰 요청의 예외도 실패로 기억한다. 다만 오류 문장이 `KisError` 모양이 아니고, 일시적인 응답 깨짐이 다시 시도 없이 그 종목의(토큰이면 그 실행 전체의) 실패가 된다.
- **지금 못 고치는 이유.** 실제 KIS에서 이런 응답이 나오는지 보지 못했고(가짜 서버만), 다시 시도할 오류의 범위를 넓히는 동작 변경이라 KIS 오류 분류·재시도 횟수 테스트를 함께 바꿔야 한다.
- **방법.** `_call`에서 `httpx.HTTPError` 전체를 잡아, 전송 오류만 다시 시도하고 나머지는 가린 `KisError`로 바꾼다. 깨진 본문 응답으로 테스트를 더한다.

## Claude가 프로필 응답 모양을 형식 강제로 받는지 확인하지 않았다
- **증상.** 프로필 추출은 Claude 모델에서도 응답 모양(`CompanyProfile`)을 디코딩 문법으로 강제한다(`constrained=True`). 재무 분석 응답은 같은 방식이 "compiled grammar is too large"로 거절된 적이 있다. 프로필 추출은 가짜 AI로만 시험했다.
- **영향.** 거절되면 모든 회사가 `AI 오류: BadRequestError…`로 실패해 빌드가 `incomplete`로 끝난다(시험 실행이면 이웃 표가 모두 "프로필이나 임베딩이 없어…"). 거절된 요청이라 AI 비용은 거의 들지 않는다.
- **지금 못 고치는 이유.** 실제 Anthropic 호출로만 확인할 수 있고, 프로필 모델 자체가 시험 실행 뒤에 정해진다.
- **방법.** 첫 시험 실행(`peers build --pilot --codes …` 몇 곳)에서 확인한다. 거절되면 재무 분석처럼 형식 강제 없이 검증하는 경로(`constrained=False`)로 바꾸거나 OpenAI 모델을 쓴다.

## 테마 검색의 용어 일치 조회를 실제 DB로 확인하지 않았다
- **증상.** 질의 용어를 가진 프로필을 찾을 때 `terms` 배열 겹침(`ov`)에 값마다 큰따옴표를 붙인 배열 글자(`{"legacydram","dram"}`)를 직접 만들어 넘긴다. postgrest-py는 목록을 받으면 값을 따옴표 없이 쉼표로만 잇기 때문에(`{a,b}`), 쉼표·중괄호·공백·따옴표가 든 열쇠가 깨지지 않게 하려는 것이다. 이 글자가 PostgREST를 거쳐 그대로 PostgreSQL 배열로 풀리는지는 가짜 DB에서만 확인했다.
- **영향.** 잘못 풀리면 테마 검색의 세 순위 중 용어 일치 순위가 비거나 틀려, 질의 용어가 사업 요약에 그대로 들어 있는 회사가 결과에서 밀린다(임베딩 두 순위는 그대로).
- **지금 못 고치는 이유.** 실제 DB에 공개 빌드가 있어야 확인할 수 있다.
- **방법.** 첫 공개 빌드 뒤 "레거시 DRAM"처럼 용어가 분명한 검색에서 결과의 `matched_terms`가 채워지는지 본다. 비어 있으면 PostgREST가 받는 요청 주소의 `terms=ov.…` 값을 로그로 보고 배열 글자를 고친다.

## 상태 줄이 평일 휴장일에 주가를 잘못 경고한다
- **증상.** 기대 거래일 규칙은 평일만 알고 공휴일·임시 휴장일을 모른다. 평일 휴장일에는 20:00부터 다음 거래일 주가가 들어올 때까지 상태 줄이 빨간색 `주가가 … 기준으로 밀려 있습니다`를 보여 준다.
- **영향.** 거짓 경고다. 문장 끝에 늘 `휴장일이면 정상입니다`를 붙여 줄였다. 진짜 밀림을 놓치지는 않는다.
- **지금 못 고치는 이유.** 휴장일 정보의 출처(KIS의 휴장일 조회, 손으로 관리하는 목록)를 정해야 하고, 그 출처가 또 하나의 갱신 대상이 된다.
- **방법.** 주가 갱신이 휴장일 정보를 함께 받아 저장하고, 상태 줄 규칙이 그것을 본다.

## 리포트 수는 텔레그램 수집·분류가 따라잡혀 있어야 맞다
- **증상.** 유사 기업 화면의 리포트 수는 이 앱이 텔레그램에서 모아 분류까지 끝낸 리포트만 센다. 수집이 멈추거나 분류가 밀리면 최근 리포트가 빠져, 증권사 리포트가 있는 회사가 `few`나 `none`(리포트 없음)으로 보인다.
- **영향.** 가장 중요한 판정인 "리포트 없음 + 아직 덜 오름" 후보가 틀린다 — 증권사가 다루는 회사가 후보로 뜬다.
- **지금 못 고치는 이유.** 운영 상태의 문제다. 수집은 아직 사람이 돌리고(예약 작업이 아님), 따라잡기는 사용자와 함께 한다.
- **방법.** 상태 줄의 리포트 기준일이 빨간색이면 리포트 수를 믿지 않는다. 수집을 예약 작업으로 만들고(텔레그램 세션 파일이 있어야 한다) 상태 줄로 지켜본다.
