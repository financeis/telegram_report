# 아직 못 푼 문제

## `tag escalate`가 상태를 확인하지 않고 덮어쓴다
- **증상.** `tag escalate --since <시각>`이 대상 `review_needed` 행을 고른 뒤 `id`로 다시 분류해 쓴다. 고른 뒤 쓰기 전에 사람이 검토 화면에서 같은 행을 승인·제외·재분류하면, 그 검토 결과를 재처리 결과가 덮어쓴다.
- **영향.** 검토한 행의 결과가 사라진다(되돌리기 스냅샷도 "후속 작업이 처리한 보고서"로 거절된다). 검토 화면과 `escalate`를 동시에 쓸 때만 생긴다.
- **지금 못 고치는 이유.** 재처리 명령의 동작을 바꾸는 일이라 사용자가 정해야 한다. 쓰기에 상태 조건을 넣으면 "덮어쓰지 못한 행"을 보고하는 방식과 테스트도 새로 정해야 한다.
- **방법.** 쓰기 SQL에 `tagging_status = 'review_needed'`(또는 가져가기 표시) 조건을 넣고, 조건에 걸린 행은 보고에 따로 센다.

## `tag run --row-ids`가 상태와 상관없이 다시 분류한다
- **증상.** 지정한 행을 `pending`으로 가져가는 표시 없이 바로 분류해 쓴다. 같은 행을 다른 작업자가 `processing`으로 가져간 상태면 둘이 겹쳐 쓴다(마지막 쓰기가 이긴다).
- **영향.** 백필 중에 `--row-ids`를 돌리면 같은 행이 두 번 분류되고 토큰이 두 배로 든다. 데이터 모양은 어느 쪽이든 정상 분류 결과다.
- **지금 못 고치는 이유.** 명령의 동작을 바꾸는 일이라 사용자가 정해야 한다. `--row-ids`는 이미 `auto`·`verified` 행을 다시 분류하는 유일한 길이라, 막는 대신 가져가기 표시를 붙이는 방식으로 바꿔야 한다.
- **방법.** `--row-ids`도 `FOR UPDATE SKIP LOCKED`로 가져가기 표시를 붙이고, 이미 `processing`인 행은 건너뛰고 보고한다.

## 종목표에서 사라진 종목은 관심 기업에서 뺄 수 없다
- **증상.** `PUT /api/favorites/{code}`는 켜기·끄기 모두 먼저 종목표에 그 코드가 있는지 본다. 종목표를 새로 바꾸면서 빠진 종목(상장 폐지 등)은 끄기 요청도 404 `종목을 찾을 수 없습니다.`다.
- **영향.** 화면의 관심 기업 목록에 그 코드가 계속 남는다. 파일(`~/.review_viewer/favorites.json`)을 손으로 고쳐야 한다.
- **지금 못 고치는 이유.** 동작을 바꾸는 일이라 사용자가 정해야 한다(지금 동작은 테스트로 고정돼 있다).
- **방법.** 끄기(`enabled: false`)는 존재 확인 없이 허용한다.

## 깨진 관심 기업 파일이 두 번째로 깨지면 기업 목록이 503이 된다
- **증상.** 관심 기업 파일이 깨지면 읽을 때 `favorites.json.bak`으로 이름을 바꾸고 빈 목록으로 본다. UTF-8이 아닌 파일도 같은 길로 간다. 이미 `.bak`이 있으면 윈도우에서 이름 바꾸기가 실패해 `GET /api/workspace`가 일반 503으로 끝난다.
- **영향.** 기업 검색·관심 기업 화면이 막힌다. `.bak` 파일을 지우면 회복한다.
- **지금 못 고치는 이유.** 동작을 바꾸는 일이라 사용자가 정해야 한다(지금 동작은 테스트로 고정돼 있다).
- **방법.** 이름 바꾸기를 `os.replace`로 해서 기존 `.bak`을 덮어쓰게 한다(또는 `.bak` 이름에 시각을 붙인다).

## 같은 PDF가 여러 메시지로 들어오면 두 번 센다
- **증상.** 행의 정체는 `(채널, 메시지 번호)`다. 같은 PDF가 다른 메시지로 다시 올라오면 별도 행이 되어, 리포트 목록과 커버리지 집계에 두 번 나온다. `file_hash_sha256`은 저장돼 있지만 묶지 않는다.
- **영향.** 커버리지 숫자(종목별 다뤄진 횟수, 발행량)가 부풀 수 있다. 분석·분류 비용도 두 번 든다.
- **지금 못 고치는 이유.** 같은 PDF를 하나로 볼지, 어느 행을 남길지(먼저 받은 것? 분류가 끝난 것?)는 사용자가 정할 업무 규칙이다.
- **방법.** 규칙이 정해지면 수집 때 같은 지문의 기존 행을 찾아 표시하거나, 집계 쪽에서 지문 단위로 센다.

## 재무 추출 프롬프트가 목표주가 방향 값으로 `유지`를 안내한다
- **증상.** 추출 프롬프트의 정규화 규칙 3은 `target_price_dir`을 `상향 / 하향 / 유지 / 신규 / N/A`로 안내한다. 응답 스키마와 DB 제약이 허용하는 값은 `상향·불변·하향·신규·N/A`다(`유지`는 투자의견 방향의 값이다).
- **영향.** 형식을 강제하는 경로(OpenAI·Codex의 출력 스키마)에서는 모델이 `유지`를 낼 수 없어 문제가 드러나지 않는다. Claude 모델로 분석을 돌리면(형식 강제 없이 JSON을 검증하는 경로) 모델이 `유지`를 내는 순간 응답 검증이 실패해 그 분석이 형식 오류로 끝난다. 검증이 목표주가 방향을 산수로 다시 정하는 단계보다 먼저 일어나므로 목표주가가 몇 개 있든 같다. 목표주가가 그대로인 리포트(새·옛 값이 같음)에서 가장 일어나기 쉽다.
- **지금 못 고치는 이유.** 프롬프트 문구를 바꾸면 추출 결과 전체가 달라질 수 있어, 같은 리포트 묶음으로 다시 비교 측정한 뒤 사용자가 정해야 한다.
- **방법.** 규칙 3의 `유지`를 `불변`으로 고치고, 측정용 리포트 묶음으로 추출 결과를 비교한다. 스키마에 `유지`를 더하지는 않는다(DB 제약과 화면이 `불변`을 쓴다).

## 기능에 명령을 붙이면 모든 명령이 FastAPI를 불러온다
- **증상.** 기능 명령은 그 기능의 `jobs.py` 등록 함수를 공개 창구(`__init__.py`)로 내보내고 `cli.py`에 한 줄 더하는 방식이다. 그런데 `cli.py`가 창구를 import하면 창구 전체가 실행되고, 지금 기능 창구는 모두 FastAPI를 불러온다(`router`, 또는 `HTTPException`을 쓰는 `service`). 그러면 `collect`·`tag`·`--help`까지 FastAPI를 불러와, "명령 입구는 웹 패키지를 불러오지 않는다"는 입구 테스트가 실패한다.
- **영향.** 첫 기능 명령(예: 수급 데이터 받기 예약 작업)을 붙이는 순간 커밋 검사가 막힌다. 아직 기능 명령이 없어 지금은 드러나지 않는다.
- **지금 못 고치는 이유.** 해결 방식이 구조 규칙에 걸린다. 창구를 웹 쪽과 명령 쪽으로 나누거나, 창구가 이름을 늦게 불러오게 하거나, 웹 패키지를 모든 명령의 필수 설치로 바꾸는 것 중 하나를 골라야 하고, 그것은 사용자가 정할 설계 변경이다.
- **방법.** 첫 기능 명령을 붙일 때 위 셋 중 하나를 사용자와 정한다. 입구 테스트를 지우거나 느슨하게 하는 것으로 풀지 않는다.

## 커버리지 계산이 "분석 대상" 규칙의 절반을 다시 적고 있다
- **증상.** 커버리지 계산(`features/coverage/logic.py`)은 리포트 창구에서 받은 행 가운데 `out_of_scope_reason`이 비어 있는 것을 분석 대상으로 친다. 상태 조건(`auto`·`verified`)은 보지 않는다. 리포트 창구가 늘 그 두 상태의 행만 넘기기 때문에 지금은 결과가 맞다. 공용 기준의 `is_in_scope`는 운영 코드 어디서도 쓰이지 않는다.
- **영향.** 리포트 창구가 다른 상태의 행도 넘기게 바뀌면(예: 검토 대기 행까지 세는 화면을 더할 때) 커버리지가 그 행들을 분석 대상으로 잘못 센다. "분석 대상 정의는 공용 기준 한 곳에만"이라는 규칙과도 어긋난다.
- **지금 못 고치는 이유.** 계산 함수들은 상태 열이 없는 표도 받도록 짜여 있고, 그 계산을 검증하는 테스트들도 일부 열만 가진 표로 만든다. 공용 기준 규칙으로 바꾸려면 계산 함수가 받는 표의 모양(필수 열)과 테스트 자료를 함께 바꿔야 한다. 커버리지 계산의 약속을 바꾸는 일이라 그 기능을 다음에 고칠 때 함께 한다.
- **방법.** 공용 기준에 표 단위로 쓸 수 있는 판정 도우미(빈 값 처리 포함)를 두고, 커버리지 계산과 리포트 조회가 그것을 쓰게 한다. 계산 함수의 필수 열에 `tagging_status`를 더하고 테스트 자료를 맞춘다.

## 기능마다 준비 코드가 복사돼 있다
- **증상.** 종목표 준비(읽기 + 버전 경고 문구 + `NotReady`)가 기업 목록·리포트·커버리지에 세 번, DB 준비(설정 확인 + 고정 문구 + 연결)가 리포트·검토·분석에 세 번, LLM 응답 확인 도우미가 분석·비교에 두 번 들어 있다.
- **영향.** 동작은 같고 테스트도 각자 있다. 다만 새 기능을 붙이는 사람은 이 중 하나를 또 복사하게 되고, 문구나 규칙을 바꿀 때 몇 곳을 같이 고쳐야 하는지 놓치기 쉽다.
- **지금 못 고치는 이유.** 한곳으로 모으려면 공용 도우미의 자리를 정해야 한다. 종목표 준비를 공용 기준(`domain`)에 두면 `domain`이 설정 읽기(`core.settings`)를 쓰게 되고, DB 준비 실패 문구를 공용 설비(`core`)에 두면 `core`가 화면 문구를 갖게 된다. 칸 경계에 관한 설계 결정이라 사용자가 정한다.
- **방법.** 다음 기능을 붙일 때 자리를 정하고, 세 기능의 준비 코드를 그 도우미로 바꾼다(기능 쪽에는 자기 기능 이름만 남긴다).

## 화면 쪽에 분석 대상 외 사유 목록이 따로 복사돼 있다
- **증상.** `frontend/`가 사유 5개(`foreign`, `fund`, `digital`, `private`, `ir_self`)를 자기 코드에 따로 적고 있다. 공용 기준(`research_desk/domain/vocabulary.yaml`)에 사유를 더하거나 바꾸면 화면은 모른다.
- **영향.** 새 사유가 검토 화면의 선택지에 나오지 않는다(서버는 받지만 화면이 못 보냄).
- **지금 못 고치는 이유.** 화면 코드를 고쳐야 하는 일이고, 화면 코드는 화면 분할 작업에서 한꺼번에 나눈다.
- **방법.** 서버가 값 목록을 주는 주소를 두고 화면이 그것을 쓰게 하거나, 화면 분할 때 한 곳으로 모은다.
